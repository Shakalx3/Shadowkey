# Step 36 — EKA2 toolchain audit

Date: 2026-11-07

## Target constraints

The target is Nokia N95 8GB RM-320, reported firmware V 35.0.001, Symbian OS 9.2 / S60 3rd Edition FP1. The handset is ARM11-class (ARMv6 family). The source archive currently provides ARM EABI object output and a static ELF link-check, but not a Symbian E32 executable.

The legacy `6R51.APP` is an old App-DLL-style E32 image (UID1 `0x10000079`, flags `0x01000003`, one export). A successful old-E32 rewrite does not bridge the EKA1-to-EKA2 application model boundary.

## Candidate A: hpnkv/symbian-platform v0.3.0

Repository: https://github.com/hpnkv/symbian-platform

Verified directly from its public README, release metadata, and native-distribution guide:

- Latest release observed: `v0.3.0`, published 2026-10-08.
- The README states that the toolchain builds Symbian ARMv5T and ARMv6 applications, and provides Clang/LLD, native ELF-to-E32 conversion, frozen-ordinal import proxies, EXE/DLL output, and EKA2 libraries.
- The native SDK distribution guide explicitly says both ARMv5T and ARMv6 EKA2 libraries are included.
- The documented build flow produces both a linked ELF and an E32 executable under `e32/*.exe`.
- The project states that original OS DLL implementations/firmware are supplied separately; import libraries do not replace the phone's system DLLs.
- The modern runtime and GUI/networking APIs require EKA2. Its EKA1 profile is a separate ARMv5T freestanding/no-UI process for a Nokia 7610 fixture and is not suitable for this N95 GUI port.
- Native Linux SDK archives require glibc 2.39 or later. The current analysis host is x86_64 with glibc 2.41, so the documented host requirement is met.
- Latest release provides a Linux x86_64 native SDK archive of 325,624,796 bytes (SHA-256 `9be830884a5fd1b9315ea1c11571810f7a50fa673851fa392bb397c6759fec3d`). A smaller 7.5 MB Linux archive is the host SDK, not the full ARM target toolchain.

This is now the strongest concrete toolchain candidate because it explicitly supports EKA2 ARMv6 output and documents ELF-to-E32 conversion. It is not yet accepted as the working toolchain: the 325 MB SDK was not downloaded or executed in this environment, and no Shadowkey project was built with it.

## Candidate B: SymbianRevive/elf2e32

Repository: https://github.com/SymbianRevive/elf2e32

The repository exists and describes itself as an `elf2e32` fork with fixes from fedor4ever and SymbianRevive. It is a lower-level ELF-to-E32 candidate, but this audit has not built it, established a complete compatible ARM EABI compiler/linker/runtime environment, or validated the generated image against the N95 loader. It should not be treated as a complete SDK by itself.

## Environment inventory

- Host: Linux x86_64.
- glibc: 2.41.
- Clang available: 17.0.0.
- `elf2e32` executable: not found on PATH.
- `symbian` CLI: not found on PATH.
- The full `symbian-sdk-0.3.0-linux-x86_64.tar.gz` has not been downloaded.
- No N95 RM-320 firmware image, `Z:\sys\bin\GDI.DLL`, or matching FP1 SDK export/DEF set is present in the supplied archive.

## Next concrete experiment

1. Obtain the v0.3.0 Linux x86_64 native SDK and verify its release SHA-256.
2. Run its doctor/toolchain probes and build the smallest EKA2 ARMv6 GUI EXE example.
3. Inspect the produced E32 header, CPU/ABI flags, imports, UID, entry point, and loader metadata.
4. Build a minimal Shadowkey bootstrap shell against the same SDK before linking the full lifted engine.
5. Compare required platform imports against the exact N95 RM-320 firmware. An E32 file generated by the toolchain is not automatically compatible with the phone's firmware or signing/capability policy.
6. Only then port the actual runtime and GDI/FBS/AVKON/CONE integrations.

## GDI/font investigation remains a separate blocker

The latest font evidence is still callsite-level and partly cross-version. GDI ordinals 101/108/151 have not been mapped to exact S60 3rd FP1 export names/signatures. The 72-byte `TFontSpec` layout is structurally supported by the five callsites and a Symbian OS 9.3 cross-reference, but not yet verified against N95 OS 9.2 exports/ROM. The synthetic `CFont` and DrawText recorder do not rasterize glyphs.

## Decision

Adopt `hpnkv/symbian-platform v0.3.0` as the first toolchain to test, not as a proven solution. Keep the old-E32 patch writer as a format-research tool only. The next meaningful milestone is a minimal EKA2 ARMv6 E32 executable whose header/imports are inspected and whose load is verified on an appropriate emulator or the actual RM-320 handset.
